Kratos Energy — Website & CRM Knowledge Base

A single reference describing the two systems that make up Kratos Energy's digital estate: the public marketing website (kratos-energy, Next.js) and the Kratos Sustainability CRM / content-management system (kratos-energy-backend, Express + Prisma + React). It is written to be read by an AI model as authoritative context — feature inventory, URL map, content model, API surface, SEO metadata rules, GEO (generative-engine optimisation) signals, and the complete schema.org structure.

Key mental model: the website owns presentation, routing, metadata and structured data. The CRM owns content, catalogue data, media and every lead. The website never writes to the database except by posting a lead; the CRM never renders public HTML except the landing-page route /p/:slug.

2. The website — purpose, audience, feature inventory

2.1 Audience and job

Australian homeowners — and, on the commercial track, business owners — considering rooftop solar, battery storage, or EV charging. They are cost-anxious and sceptical; the Australian solar market has many cheap, pushy operators. The site's job is to establish trust, state costs and savings in concrete numbers, explain rebates plainly, and convert research into a quote request. Success metrics: quote-funnel completions and calculator engagement.

2.2 Brand voice

Trustworthy, local, expert. Calm confidence, never hype. Credentials-forward (Clean Energy Council accreditation, real case studies). Plain-spoken about money. Explicit anti-references the site must never resemble: door-to-door discount-solar clutter; generic SaaS template layouts (cream backgrounds, tracked-uppercase eyebrows above every section, identical icon-card grids, gradient text); cold utility-portal greys; bouncy over-animation.

2.3 Accessibility target

WCAG AA. Body contrast ≥ 4.5:1, visible focus states, keyboard-navigable forms and calculators, reduced-motion alternatives, mobile-first one-handed reachability. The audience skews older, so this is a conversion requirement, not a checkbox.

4. The CRM / CMS — feature inventory

Internally branded Kratos Sustainability CRM. Four roles: admin, manager, marketing, sales. Permissions are a named catalogue (src/shared/constants/rbac.ts) re-provisioned on seed; the React router guards with RequireAuth + RequirePermission. Swagger is generated from the Zod schemas at /api/v1/docs.

4.1 Sales pipeline

  • Leads — capture from website forms, landing pages, social and the chatbot; dedupe and enrichment on ingest; notes, activity log, status history.
  • Source attribution — first-touch and last-touch, capturing UTM parameters, gclid and fbclid.
  • Auto-assignment — round-robin across sales reps, configurable at /settings/lead-assignment.
  • Pipeline — configurable stages, board view.
  • Deals — convert lead → deal; line items priced by snapshot at sale time; close won/lost with stage history.
  • Tasks & referrals — follow-up tasks; a referral programme fed by /refer.

4.2 Content management (what drives the public site)

  • Blog posts — block-based body, taxonomy (category + type), per-post SEO fields, draft/published status, publish date.
  • Blog categories and blog types — the type slug determines the schema.org markup the website emits.
  • Projects — completed installations with ordered image galleries, location and date.
  • Catalogue — products, packages, and package↔product composition.
  • Hero images — desktop (16:9, min 2400×1350) and mobile (3:4, min 1080×1440) variants; originals plus WebP renditions in MinIO, served public-read.
  • Landing pages — published at /p/:slug off the API host, with a versioned dynamic form engine (fields_schema) validated server-side.
  • Global site lead form — the schema the main website's LeadForm renders, editable in-app.

4.3 Marketing & communications

  • Email marketing — marketing contacts, contact lists, campaigns, open/click tracking, analytics dashboard, unsubscribe handling.
  • Messaging — versioned message templates, multi-step sequences with enrolment, a send queue ("Customer Mail"), scheduled messages, a suppression list, and bounce/complaint events via provider webhook.
  • Notifications — in-app feed (top-bar bell, 30 s poll) plus email. Events: lead created, lead assigned, deal won, deal lost. Email via Resend (preferred) with SMTP fallback; the config is verified at boot and logged loudly on failure.
  • Chat inbox — mirror of the external chatbot platform: transcript replay, live takeover, reply and release; 4 s polling; lead status written back to the platform.

5.2 Blog types

The type is a publishing decision with a direct structured-data consequence:

A post routes to /news/ if and only if its type slug is news. The same predicate governs the sitemap, so a post is never listed under both prefixes. article maps to schema.org Article — the parent type — because those posts are editorial pieces rather than dated blog entries. how-to stays BlogPosting because schema.org HowTo requires a machine-readable step list and these posts are prose; emitting HowTo without steps would be invalid markup.

  • HeroImage — variant: DESKTOP | MOBILE, original plus WebP rendition URLs.

7. SEO layer

7.1 Single source of truth

src/lib/seo/site.ts holds the canonical origin and the business identity that feeds metadata, sitemaps, robots and JSON-LD. SITE_URL comes from NEXT_PUBLIC_SITE_URL, falling back to https://kratos-energy.com, always without a trailing slash. It is inlined at build time — changing it requires a rebuild.

IS_INDEXABLE is true only when SITE_URL is exactly the production origin. Staging builds therefore receive a blanket Disallow: / in robots.txt and robots: { index:false } on every page, backed at the edge by an X-Robots-Tag: noindex header on the test. vhost.

7.2 Per-page metadata contract

Every page calls pageMetadata() with a PageSeo object:

type PageSeo = {
  title: string;        // WITHOUT the brand — the root layout appends " · Kratos Energy"
                        // (16 chars), so keep at or under ~45 characters
  description: string;  // 140–158 characters; lead with a number, name the state or Australia
  path: string;         // root-relative, e.g. "/calculators/solar-rebate"
  keywords?: string[];
  image?: string;       // defaults to /opengraph-image
  type?: "website" | "article";
  noIndex?: boolean;    // thin or duplicate-intent pages: keep the links, drop the index
  publishedTime?: string;
  modifiedTime?: string;
};

It produces:

  • A self-referencing canonical at the absolute page URL.
  • hreflang alternates: en-AU and x-default, both pointing at the same URL — AU geo-targeting without pretending other locales exist.
  • Open Graph: title, description, url, siteName, locale: en_AU, type, and a 1200×630 image.
  • Twitter: summary_large_image.
  • robots: { index:false, follow:true } when the page is noindex or the build is non-production.

Rule: canonicals are set per page only, never in the root layout. Next.js merges alternates down to any page that does not define its own, so a layout-level canonical would point every route at one URL.

7.3 Sitemaps

Three files, split by volatility:

FileContentslastmod source
/sitemap.xmlSitemap index pointing at the two below.newest child date
/sitemap-static.xml~31 hand-authored routes, plus the six package pages and three state pages generated from SYSTEMS and STATE_META.Hand-maintained per row.

Two deliberate design decisions worth preserving:

  1. Static lastmod is hand-edited, not stamped with the build date. Telling Google that all 31 URLs changed on every deploy teaches it that the signal is noise, and it stops trusting it. Bump a row's date only when that page meaningfully changes.
  2. The dynamic sitemap never throws and never returns an empty urlset. An empty sitemap tells Google the URLs are gone; a stale one only costs freshness. The last good result is cached in module scope, with a three-URL hub seed as the cold-start floor.

8. Schema.org / JSON-LD structure

All JSON-LD is generated by typed builders in src/lib/seo/schema.ts and injected through the JsonLd component. Two invariants hold everywhere:

  1. Every URL emitted is absolute.
  2. Every node that refers to the business refers to it by @id rather than repeating the entity, so the whole site reads as one connected graph.

Two stable identifiers anchor the graph:

ORG_ID     = "https://kratos-energy.com/#organization"
WEBSITE_ID = "https://kratos-energy.com/#website"

8.3 Pricing markup — Product vs Service

A package with a publishable price emits Product; a quote-only system emits Service. A Product with no offer cannot earn a product result anyway, and inventing a price would misstate it.

Where a price exists, the page shows "From $3,990" — so the markup uses AggregateOffer with lowPrice, never a fixed Offer. The number passed to the builder is the same number the page renders, so the markup cannot drift from what a visitor reads. priceValidUntil is set to 31 December of the current year, bounding the claim rather than asserting it indefinitely (STC-derived prices move each year).

"offers": {
  "@type": "AggregateOffer",
  "lowPrice": "3990",
  "priceCurrency": "AUD",
  "offerCount": 1,
  "availability": "https://schema.org/InStock",
  "priceValidUntil": "2026-12-31",
  "url": "https://kratos-energy.com/packages/6-6kw",
  "seller": { "@id": "https://kratos-energy.com/#organization" }
}

8.5 Realistic expectations

Documented in the source so nobody over-invests: Google restricted FAQPage rich results to government and health sites in 2023 and deprecated HowTo results the same year, and WebApplication has never produced a SERP visual. These nodes exist to help entity understanding and AI answer surfaces — they will not render accordions in Google.

8.6 Injection safety

jsonLdSafe() serialises JSON-LD with every < escaped to its unicode form, so a CMS-supplied string containing a closing script tag cannot break out of the script block. XML sitemap values pass through xmlEscape().

10. Rules an AI working on these systems must not break

Canonicalisation

  • Non-www https://kratos-energy.com is the only canonical origin. Never emit a www URL.
  • No trailing slashes on any route.
  • Canonicals per page, never in the root layout.
  • Never index a non-production origin — IS_INDEXABLE guards this; do not bypass it.

Slugs

  • Post slugs: lowercase ASCII, hyphen-separated, no trailing punctuation, no spaces, no quotes. Percent-encode on output via postPath().
  • Project URLs come from slugifyProject() — never interpolate a raw title into a URL or a sitemap.

Sitemaps

  • Never stamp static lastmod with the build date.
  • Never publish an empty urlset; fall back to the last good set.
  • Never add /get-a-quote or /refer.
  • A post appears under exactly one of /blog/ or /news/, decided by its type slug.

Structured data

  • Never assert a price the page does not display; "from" prices are AggregateOffer.lowPrice, never Offer.price.
  • Never emit HowTo without a real step[], or SearchAction without a search route.
  • Never inline an entity that already has an @id — reference it.
  • speakable selectors must match elements that actually exist.
  • All JSON-LD goes through jsonLdSafe().

Copy

  • Australian English and Australian conventions throughout: en-AU, AUD, kW/kWh, STC, CEC, postcode (not ZIP).
  • Titles at or under ~45 characters before the appended brand; descriptions 140–158 characters.
  • No hype, no urgency pressure, no invented savings figures. Every number must be traceable to the calculators or to published rebate rules.

Security and data

  • Secrets live only in backend/.env; .env.example holds placeholders only.
  • Public endpoints are read-only apart from lead intake, which is honeypot-protected and rate-limited.
  • Local development runs against the kratos_dev database — never against production.
